## [Unreleased]

### Added

- **`make doctor` now reports how DEEPLY it verified, and refuses to report more depth than it reached.** Three tiers, and the word had no definition anywhere in this project before now: **tier 1** the thing exists, **tier 2** its content is not the template's, **tier 3** the value the build actually resolves is not the template's. A new `IdentityAdopted` step climbs all three against `app/Identity.xcconfig` through `bin/lib/xcconfig.rb`, the one reader — the file is a regular file; each of `BUNDLE_ID`, `APP_PRODUCT_NAME`, `DISPLAY_NAME` and `COPYRIGHT` is non-empty (a comment-only `= // disabled` is empty, not present), is not an identity this template has ever shipped in any letter case, and is not the `TODO Copyright` placeholder, and `.bootstrap.env`'s `APP_NAME`/`BUNDLE_ID` agree with it; then `xcodebuild -showBuildSettings` reports `PRODUCT_BUNDLE_IDENTIFIER` and `PRODUCT_NAME` equal to the parsed values. A failure names the tier **and the offending value** and exits 2; a success prints `verified to tier 3: …` rather than a bare ✓. **Depth that could not be measured never renders as depth that was**: no `xcodebuild` or no generated project is an explicit `verified to tier 2; tier 3 not reached: <reason>`, and an `xcodebuild` that fails outright is reported as *no verdict*. **The guard lives in the runner, not in the steps.** A step declares the minimum depth at which its `done` means anything and `Runner#render_result` downgrades a `done` from below it to blocked — because the defect this exists to prevent is a step trusting itself. That is not hypothetical: `Icon1024` compared the icon's bytes against `ICON_1024_PATH`, so pointing `ICON_1024_PATH` at the placeholder reported `done` — presence verified, content never examined — and the placeholder reached a human App Store reviewer as a Guideline 2.3.8 rejection, one full review cycle, with every CI cell green. `Icon1024` now runs `ci/check-app-icon.sh` (the script that exists because of that) as its tier-2 content check, capturing the script's stderr so the block quotes the actual reason rather than the script's banner. Every tier was observed red under bundler before the step was trusted, on fixtures rather than on tracked files: the template bundle id → `tier 2 failed: BUNDLE_ID = … (template identity)`, exit 2; a `.bootstrap.env` disagreement → the D-59 message carrying both values, exit 2; a byte-identical copy of the placeholder icon (so the old hash check passed) → blocked with `spread 0, need >= 40`, exit 2; the project moved aside → the tier-3 warn at the baseline exit code; and the live tree → `verified to tier 3: com.indiagram.shipkitpipes.ios / ShipkitPipes`. Two fixture knobs (`IDENTITY_XCCONFIG`, `BOOTSTRAP_ENV`) each print a banner on stderr every time they are honoured, so a run against a fixture can never be mistaken for a run against this repository. `Config::REQUIRED_ALWAYS` is deliberately untouched — removing the `.bootstrap.env` identity keys would break the very command this change improves — and the tier vocabulary is applied to the two identity steps only; the other nineteen still report status without depth. Recorded as `UL-041`.

- **A secret scan on every pull request: a pinned, checksum-verified gitleaks binary reading git history, and an allowlist that is itself a gate.** `tools/gitleaks.rb` downloads the pinned gitleaks **8.30.1** release tarball, verifies its sha256 against the digest published in that release's own checksums file *before* unpacking or executing it, confirms the binary reports the pinned version, and scans the full history reachable from `HEAD` with `--exit-code 42`. It runs as a separate named step inside the already-required `review notes` job — not as a new job, which would be a tenth status context that runs, reports and blocks nothing — and the checkout for that job is now `fetch-depth: 0`. **It is the binary and not the project's GitHub Action** because that Action requires a commercial licence for organisation-owned repositories, which this is, while the binary is MIT; the Action's name is deliberately unspelled in both files so a grep for it cannot be satisfied by a comment explaining its absence. **The scan reads history, not the working tree**, because a credential committed and then deleted in a later commit is found by the first and missed entirely by the second — measured both ways on the same clone; deleting a secret in a follow-up commit does not unpublish it. **And `fetch-depth: 0` is deliberately not the gate:** on a depth-1 clone the same verified binary with the same flags reports `1 commits scanned … no leaks found` and exits 0 with the token sitting in history, so the wrapper asserts `git rev-parse --is-shallow-repository` itself and refuses (exit 2) — one YAML line anybody can delete is not a check. It refuses a target that is not a git repository for the same reason, and refuses after the fact if the scan printed no commits-scanned line at all. Exit codes are separated on purpose: 0 clean, 42 findings, 1 the scanner ran and failed for another reason (a malformed config exits 1 by default, which is also the default exit for findings — with the default, a broken allowlist and a leaked key are the same number), 2 cannot run. A finding prints its rule, file, line and commit with the secret itself `REDACTED`. **`.gitleaks.toml` is required rather than optional**: under the built-in rules this repository fails its own scan with ten findings, every one a documentation placeholder or an `ENV.fetch` example, and a gate that is red on a clean tree is a gate somebody switches off. Its three entries are dated and each scoped to a literal or a path. **Because an allowlist is where the hole gets drilled, it has its own test.** `test/gitleaks_config_test.rb` rejects a catch-all or under-six-character regex, a line-target entry without paths, a description not beginning with an ISO date, a `paths` row matching no tracked file, and any key the scanner would ignore silently; it also compares the version pin in its two deliberate homes, the wrapper that executes it and the step name a reader sees in the Actions log. Every failure mode was observed before the gate was trusted, in scratch clones outside the repository: a tampered digest refused; a depth-1 clone refused while the raw binary passed it; a high-entropy token generated from `/dev/urandom`, committed and then removed, found at exit 42 while a working-tree scan of the same clone exited 0; a catch-all allowlist entry swallowing that token at exit 0, rejected by the config test, and red again once removed. The fake token was generated from `/dev/urandom` because a low-entropy one is not detected at all — `ghp_` plus 36 identical characters, and AWS's own documented example key, both report nothing — so a control built from one would prove nothing. **What a green badge does not cover, stated rather than implied:** the scan follows `HEAD`'s ancestry, so commits on other refs are out of scope, and specifically commit `33f8e08` (a real given name in a fixture, off `main` via squash and reachable only by SHA) is not covered and remains a separate human action; a secret that was never committed is not in git at all; and gitleaks detects neither a low-entropy fake nor a credential format its rules have never seen.

- **Personal information is gated by a fail-closed domain allowlist, and no workflow may read `vars.*` outside one frozen file.** `tools/check-contamination.rb` grew two more rules. The first: every address-shaped string in every tracked file fails unless its DOMAIN carries a row in the new `tools/domain-allowlist.txt` whose local part admits it. Fail-closed is the point — a deny-list of known-bad values catches only what someone already thought of and stays green for every address nobody has thought about yet, which is precisely the case a gate exists for — and the organisation's mail domain carries exactly one row, for the contact `SECURITY.md` and `CODE_OF_CONDUCT.md` publish, so the two role addresses this repository had grown fail by the *absence* of a row rather than by anyone remembering to look. Six rows, each a domain, a permitted local part, an ISO date and a reason; domains compared case-insensitively and local parts exactly, because RFC 5321 leaves local-part case to the receiving host. **The list is itself a gate**, in the same five ways the identity allowlist is: a wildcard or non-hostname domain cell, an undated or malformed row, a duplicate, and a row that matches no address anywhere each fail — the wildcard refusal being the load-bearing one, since a catch-all row is the single character that would turn a fail-closed list into a blanket exemption. **The regex has a built-in false-positive class, and it is excluded in code rather than by a row**: the address expression already used to sweep five fork-owned documents matches the macOS icon filenames when run tree-wide (`icon_<size>@2x.png` parses as local-part @ domain . tld — twelve occurrences in four tracked files), so one anchored expression removes that class before the address regex runs. A path exemption would have blinded the gate to a real address in the same file and a `.png` domain row would have admitted any local part on a pretend TLD. That exclusion was *proven* load-bearing rather than assumed harmless: commented out in a scratch copy of the gate, the run turned fourteen lines red, while a `@2x.io` lookalike is still reported with the exclusion in place. The second rule freezes the `vars.*` surface: one file (`.github/workflows/dependabot-automerge.yml`) and one number (three lines), with every other `vars.` read under `.github/workflows/` failing by file and line, a fourth read in the allowlisted file failing too, and a tree that has workflows but has lost that file reporting `found 0` rather than `0 reads`. That is the durable half of the property that a fork's pull request behaves identically to an internal one — the repository variables are gone, and this is what keeps them gone. Both rules were driven red on the live working tree before being trusted: an address on an unknown domain, the removed role address re-added to a workflow, a catch-all row appended to the allowlist, the icon exclusion removed from a scratch copy, and a stray `vars.APP_NAME` added to a required workflow — each restored and the tree confirmed clean between them. Measured at the end: 147 files scanned, 62 addresses seen, **0 unallowed**, 3 `vars.` reads, **0 unallowed**. The gate still has zero `require` lines. **Two addresses were resolved at their source rather than allowlisted**: `CODE_OF_CONDUCT.md` and `SECURITY.md` now publish the maintainers contact instead of a role address named after this repository, and `bin/refork-smoketest.sh` seeds a recreated repository with that same contact and uses an RFC 2606 `.invalid` identity for its throwaway orphan-commit author. The `.invalid` treatment was deliberately not applied to the two governance documents — a privacy rule that leaves a public repository advertising an undeliverable vulnerability-disclosure channel has traded a smaller harm for a larger one, which is recorded as `UL-039`.

- **A whole-tree contamination gate, and an identity allowlist that is itself a gate.** `tools/check-contamination.rb` reads every tracked file's working-tree content and fails on any occurrence of the template's identity — both of them, since the one-time sync with apple-shipkit brought upstream's placeholder in alongside this fork's original one — in any letter case, unless a row in `tools/identity-allowlist.txt` permits it. It is fork-owned Ruby in `tools/` with zero `require` lines (so the `review notes` job keeps `bundler-cache: false`), and it runs on every pull request inside that already-required job along with its contract test. **It is not `ci/check-identity.sh`, and the header says so**: upstream's script is a *completeness* check — is the fork's own identity present and non-empty where the build needs it — while this one is a *contamination* check, and a green run of either says nothing about the other. It is also not at `bin/check-identity.sh`, which is what the requirement's wording named: `bin/` and `ci/` are template-owned and `bin/refork-smoketest.sh` recreates this repository from the template, so a fork-authored file at a template-owned path is deleted wholesale on the next refork — silently removing the gate. **The reason the tree is not simply swept clean** is that roughly forty tracked files legitimately carry the literals, in five distinct classes, and one of those classes is guards: `bin/adopt.rb` refuses to adopt a live App Store app while the bundle id is still the placeholder, and `fastlane/Fastfile`'s `adopt_existing_app` guard does the same. A check that rejects a placeholder must spell the placeholder it rejects, so a gate that deleted every occurrence would delete the guards. **The allowlist is therefore driven red too**, because an allowlist that can silently permit everything is the same defect class as a gate that cannot fail. Every row is a dated measurement triple — path, expected COUNT, ISO date — plus a reason opening with its class name, and the gate fails on a row that matches nothing, a row whose count is short or long, an undated or malformed row, a duplicate row, and a `*` row for any path but `CHANGELOG.md` (which gains mentions every phase, and whose `*` row still fails if it ever stops matching). The count is the load-bearing part: a path-level exemption exempts the whole path, so a real regression standing beside a legitimate guard literal would pass — that exact scenario was staged on the live tree, a `|| "…"` fallback re-added to `fastlane/Fastfile` two lines from its guard, and the count caught it. Seven red controls were recorded on the live working tree before the gate was trusted, each restored and the tree confirmed clean between them. Measured at the end of the change: 146 files scanned, 15 skipped as binary, 41 allowlisted, **0 unallowed** — and no row under `app/` (the six occurrences that shipped in the binary were removed earlier in this phase, and the contract test asserts no row can quietly put them back) and no row permitting configuration that anything actually reads.

- `docs/APPLE-ACCOUNT-STATE.md` — the tracked, durable record of Apple account operations state: enrollment type, the two agreement windows and their shared `May 16, 2027` expiry, the App Store Connect API key's identity and its verified *absence* of an expiry, and the per-type certificate census for the shared team. It exists because the reasoning behind these values lives in gitignored planning notes that do not survive a fresh clone, and because the pre-submission checklist needs the values themselves rather than the argument for them. Every row is a triple — value, ISO-8601 measurement date, and the team or key or record it was measured against — which is a direct response to a defect this repository already carries: `.github/workflows/release.yml` records certificate-capacity figures measured against a *different* Apple team, and nothing in that file says so, so there is no way to tell a number that applies from a number that was copied forward. Rows that have not been measured yet say `pending NN-NN` and name the plan that will measure them, so a blank is never mistaken for a zero. The file records occupancy and never a quota, because Apple publishes no numeric per-team certificate figure at all and the only honest thing to record is what was counted, on a date. It publishes a close-out check as a section-scoped `ruby -e` parse rather than a grep, because the document prints its own column names and an example header row, and a whole-file grep would match the prose describing the check — the same near-miss recorded three times in `docs/UPSTREAM-LEDGER.md` as UL-010. No personal information is recorded: the App Store Connect Business page displays a good deal of it, none is needed here, and `test/docs_structure_test.rb` now sweeps this file for contact-address-shaped strings along with the other four fork-owned documents.

- `bin/verify-asc-agreements.rb` + a "Verify ASC agreements are in effect" preflight step in `release.yml` and `canary-local-mode.yml` — probe App Store Connect up front and, if a required Apple agreement is missing/expired, fail fast with an actionable runbook (which ASC screens the Account Holder must accept) instead of surfacing cryptically deep in `compute-release-tag.rb` / mid-cert-mint / at upload. Surfaced 2026-07-11 when the Saturday canary went red across **all** cells (both generators, CI-mode and local-mode) with `A required agreement is missing or has expired` — Apple gates the entire ASC API behind an in-effect agreement, so the failure was account-wide (even the xcodegen cell, unrelated to the concurrent tuist work, failed). Mirrors `canary-trigger.yml`'s PAT-expiry preflight (#248). Implementation: `Bootstrap::AscAgreementError` (detects Apple's agreement-gate message and carries the runbook), `Bootstrap.verify_asc_agreements!` (minimal account-wide `App.all` probe), and `Bootstrap.setup_asc_token_from_env!` (shared ASC-token-from-env setup for the CI path). `bin/lib/version_resolver.rb`'s `next_build_number` now also translates the agreement error to the same actionable message, so a human running `make ship` gets it too — not just the CI preflight step.

- `tools/gen-review-notes.rb` + `.github/workflows/review-notes.yml` + `test/gen_review_notes_test.rb` / `test/docs_structure_test.rb` — make the text App Review actually reads an artifact of the text that was reasoned about, instead of a second copy of it that drifts. `docs/REVIEW-ARGUMENTS.md` is now the source of truth and `fastlane/metadata/review_information/notes.txt` is generated from a delimited block inside it; what it replaced was the scaffold's `TODO:` placeholder, which ships to Apple verbatim if nobody notices in time. The check deliberately asserts more than a file diff: `read_review_field` in the Fastfile resolves `ENV[APP_REVIEW_NOTES]` *ahead of* `notes.txt`, and `.bootstrap.env.example` actively recommends setting that variable — so a check that only compared the document against the generated file would report green while Apple received text nobody in this repo had read. `--check` therefore fails if `APP_REVIEW_NOTES` is set in either the process environment or `.bootstrap.env`, which is the only form of the check that guarantees the property it exists to guarantee. The gate is a **new fork-owned workflow** rather than a job added to `pr.yml`, because the existing workflows are template-owned; the generator is dependency-free (zero `require` statements) so CI installs nothing. Known failure mode, disclosed rather than papered over: the workflow's `review notes` job is a required status check on `main`, and `bin/setup-github.sh` recomputes the required-checks array from the platform matrix and PUTs it wholesale, so any `make setup-github` (or `bin/refork-smoketest.sh`) run silently drops the requirement — the workflow keeps running and keeps reporting, and a red drift check simply stops blocking the merge. `docs/CONTRIBUTING-UPSTREAM.md` carries the idempotent restore command; verify by counting **nine** required contexts, not by looking at the Actions tab, because a de-required check looks exactly like a required one.

- `docs/PRODUCT-IDENTITY.md`, `docs/REVIEW-ARGUMENTS.md`, `docs/CONTRIBUTING-UPSTREAM.md`, and `docs/UPSTREAM-LEDGER.md` — four fork-owned documents, tracked so they survive a fresh clone rather than living in untracked planning notes. `PRODUCT-IDENTITY.md` records the App Store display name, the bundle identifiers, and the v1 tool-to-surface map. ### Changed

- **The two xcconfig-reader defects went upstream as one pull request, because they are one defect.** `apple-shipkit` [#282](https://github.com/indiagrams/apple-shipkit/pull/282) carries `bin/lib/xcconfig.rb` and its 51-check contract test; it deletes the template's `defines_non_empty?` predicate, which accepted `BUNDLE_ID = // temporarily disabled` because `\S` matched the first `/` while Xcode resolves that key to nothing and drops it from `-showBuildSettings` entirely (`UL-031`), and it replaces `ci/local-release-check.sh`'s `PRODUCT_BUNDLE_IDENTIFIER:` grep of `app/project.yml`, which since the template's own identity move returns the literal `$(BUNDLE_ID)` — so the `-z` guard below it cannot fire and the unresolved reference reaches ExportOptions as a provisioning-profile dict key, failing only after a full signed archive (`UL-032`). **One pull request rather than two because the learning is one**: a hand-rolled reader of this format is correct about the value it was written against and wrong about the next one. And one parser rather than a tighter predicate because the release half needs a *value* rather than a yes/no, so a stricter gate would have left a second reader standing to disagree with the first. Hand-authored in a separate clone against upstream's own text at `c6c324f` per `docs/CONTRIBUTING-UPSTREAM.md` §4 — **nothing was pushed from this repository**, whose `upstream` push URL is still `no-push`. Both defects were reproduced RED against upstream's unmodified files under Ruby 3.3.12 and 4.0.6 before the fix went in, the 779 added lines were swept for every value of this fork's identity (all zero, the Team ID compared without being printed), and the SCOPE test is cited and answered in the PR body. `UL-031` and `UL-032` move from `Pending` to `Submitted [#282]`; the fork's own `bin/preflight-identity.rb` and `ci/local-release-check.sh` stay divergent from the template's until it merges (`UL-034`). It is not merged, approved or auto-merged from here — review belongs to upstream.

- **The cross-generator parity tool can now see the two things that escaped Phase 3 — the unit-test bundles' `TEST_HOST` and the built `Info.plist` — and each half was watched failing before it was believed.** `tools/identity-parity.rb` compared only the app targets' resolved identity keys, and both Phase 3 escapes were invisible to it for the same structural reason: the thing that was wrong was somewhere the tool never looked. `TEST_HOST` and `BUNDLE_LOADER` live on the TEST targets, and both schemes' build actions contain only the app target, so the dump the tool filtered carried no `TEST_HOST` line at all — a longer key list would have found nothing and reported parity, which is a gate that cannot fail. It now dumps each unit-test bundle with `-target` and compares `TEST_HOST` against the HOST app target's own resolved `BUILT_PRODUCTS_DIR` + `EXECUTABLE_PATH` (a second dump with the same flags — never a literal, so no expectation goes stale on a rebrand), asserts `BUNDLE_LOADER == TEST_HOST`, and compares the two generators' `TEST_HOST` to each other. The second half opens the artefact: unless `--skip-plist`, each app is BUILT unsigned into a scratch derivedData tree and `CFBundleIdentifier` / `CFBundleDisplayName` / `CFBundleName` / `NSHumanReadableCopyright` are read with `plutil` and compared to `BUNDLE_ID` / `DISPLAY_NAME` / `APP_PRODUCT_NAME` / `COPYRIGHT` as `bin/lib/xcconfig.rb` resolves them, with the `©` printed as bytes on every run; the bundle is located from `BUILT_PRODUCTS_DIR` + `INFOPLIST_PATH` of a dump taken with the build's own flags, never by `find`. Both halves were driven RED first and restored: `app/project.yml` given `UL-027`'s literal `App-iOS.app/App-iOS` spelling (and, separately, the `$(TARGET_NAME)` one, which resolves in the test target to `AppTests.app/AppTests`) each produce a diff and exit 1; `DISPLAY_NAME = Negative Control` with the bundle deliberately NOT rebuilt shows the artefact still reading `Shipkit Pipes` against a file saying otherwise, exit 1, and the same bundle rebuilt reads `Negative Control`. A nonexistent unit-test target exits 2 naming it, because “the target was not there” must never read as “it checked out”. `--skip-plist` changes the verdict line to `PARITY OK (build settings only; plist half skipped)`, since a skipped half that reads as full parity is the same defect one level up, and `--reuse-build DIR` reuses an existing bundle loudly rather than silently. The tool runs the `build` action only and never the test one: an unsigned UI-test runner raises a Gatekeeper dialog on the operator's desktop. It remains a LOCAL command with dated evidence rather than a CI gate, which is decided rather than defaulted — the diff needs Xcode, the fork's only workflow runs on `ubuntu-latest`, and all three `macos-15` jobs live in template-owned `pr.yml`. Its first run found something no control had staged, now `UL-043`: Tuist writes one platform-free `TEST_HOST` (`…app/$(BUNDLE_EXECUTABLE_FOLDER_PATH)/$(APP_PRODUCT_NAME)`) whose variable is EMPTY on iOS, so Tuist's resolved iOS value carries a double slash where XcodeGen's has one — the same file, and both cells green, so the comparison is POSIX-normalised and prints a `NOTE` naming both raw strings whenever normalisation is what made them equal. ### Removed

- **BREAKING**: Removed `~/code/.bootstrap.env` cross-fork auto-sourcing convention. The Makefile's `_PARENT_ENV` macro and `_LOAD_PARENT_ENV` shell-source no longer exist; every `make` target invokes its driver directly without auto-sourcing any file outside the fork. The short-lived `Bootstrap::CrossForkConfigLeak` doctor step from #234 (added 2026-05-12 to detect abuse of the convention) is removed as part of this since the footgun it detected no longer exists. Surfaced 2026-05-12 by the maintainer auditing the codebase: a specific filesystem layout (`$HOME/code/.bootstrap.env`) was hardcoded into 9 surfaces of the template (Makefile, bin/lib/bootstrap.rb, bin/adopt.rb, fastlane/Fastfile, .bootstrap.env.example, README, AGENTS.md, docs/BOOTSTRAP.md, docs/GETTING-STARTED.md) — convention bleed from the maintainer's personal codebase organization. The Fastlane lanes' env-first behavior (ENV wins over file) is preserved unchanged, so all the documented mechanisms continue to work; the template just doesn't bake in an opinion about WHERE those env vars come from. - **Release tag format → `v<MARKETING>+<BUILD>` (e.g. `v1.0.0+5`)**, replacing the previous CalVer-as-marketing-version scheme (`v2026.19.1357`, `v2026.19.1`). The old scheme conflated "which run shipped this" with "what marketing version users see" — every ship invented a new `CFBundleShortVersionString`, fragmenting TestFlight into one "Version X" bucket per ship (the user-visible symptom: 6 buckets after 6 ships, App Store submission flow ambiguous, testers scrolling past dozens of obsolete entries). Result: **one TestFlight "Version 1.0.0" bucket holding all builds shipped at marketing 1.0.0**; bumping marketing version is intentional (= "this release introduces real changes worth telling users about"). New `bin/lib/version_resolver.rb` (Bootstrap::Version) + `bin/compute-release-tag.rb` CLI used by both local-mode `bin/ship.rb` and CI-mode `release.yml`'s "Compute release tag" step. ## Versioning

This CHANGELOG tracks **template versions** — releases of the `apple-shipkit` repo itself, not the forker apps that consume it. Forker apps maintain their own CHANGELOG and version policy independently.

Pre-1.0 (`0.x`) is the development phase: breaking changes are allowed without bumping a major version. The `0.x` retrospective entry above summarizes what shipped during M1–M4 milestones; further pre-1.0 work lands under `[Unreleased]` until the public flip.

`v1.0.0` was cut at the public-visibility flip (2026-05-01). From `v1.0.0` onward this project follows strict [Semantic Versioning](https://semver.org/spec/v2.0.0.html): `MAJOR.MINOR.PATCH` where MAJOR is incremented for breaking forker-facing changes (renamed `bin/` scripts, removed Make targets, restructured README sections that forkers cite), MINOR for new forker-facing features (new scripts, new sections), and PATCH for fixes that don't change the forker contract.

Forkers tracking template upgrades should read the CHANGELOG before pulling template changes into their fork. Template-fork creation always uses the default branch (`main`); to base a fork on a specific template version, use `git fetch` to pull a specific tag and rebase manually.

## Tagging

When cutting a release:

1. Move the `[Unreleased]` entries into a new `[X.Y.Z] - YYYY-MM-DD` section in `CHANGELOG.md` and commit.
2. Extract the new section to a release-notes file: `awk '/^## \[X\.Y\.Z\]/{flag=1; print; next} flag && /^## /{exit} flag' CHANGELOG.md > release-notes.md`.
3. Create an annotated tag with the release notes as its message, push, and create the GitHub release.

```bash
# After moving Unreleased → [X.Y.Z] in CHANGELOG.md, committing,
# and writing release-notes.md (the new section's body):
git tag -a vX.Y.Z --cleanup=verbatim -F release-notes.md   # annotated tag; --cleanup=verbatim preserves Markdown headings (default --cleanup=strip eats #-prefixed lines); -F reads notes from file
git push origin vX.Y.Z
gh release create vX.Y.Z --notes-from-tag --title "vX.Y.Z" --verify-tag
```
